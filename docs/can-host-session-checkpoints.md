# 调参上位机串口会话修正（2026-09-26）

适用于 `llm-pid-tuner-main` 的 Python 程序及调用它的启动脚本。此次没有修改固件、PID 配置或固件保护门槛。

## 证据与边界

最新附件显示：串口监视期间四轮反馈新鲜且序号递增；出现 `CAN RECOVERED` 后，反馈序号冻结，年龄增长到约 36–39 秒。附件没有切换瞬间的命令流和 CAN STATUS，无法据此确定是开串口、主机接管、模式切换还是运动负载触发故障。`RECOVERED` 也不等于之后的反馈持续恢复。

## 已修改

- 串口打开前设置 DTR/RTS 为低并关闭流控，避免应用主动使用默认置位值；驱动/适配器是否仍产生瞬态需实机验证。
- 初始 STOP 应答后继续等待 `MOTOR STOP STATUS` 的 CONFIRMED 和 FRESH=1，再发送 HOST LINK COM，避免停车尚未完成就重新接管。
- HOST LINK 后、MODE TUNE 后、每轮启动前均读取连续 CAN STATUS/MOTOR FEEDBACK。要求 CAN 就绪、ESR 无当前警告/被动/离线标志、TX_OK 增长且 TX_ERR/TX_TIMEOUT 不增长、所需电机反馈年龄不超过 300ms 且 SEQ 递增。历史错误计数非零本身不导致拒绝。
- 退出先查询停车状态；已确认且新鲜则不重复 STOP，否则发送 STOP 并等待确认。查询失败仍尝试 STOP。退出不再自动发送 MODE WORK（该命令有电机/执行器操作副作用）。
- 保留串口超时拆开的半行，避免把半条状态当成完整应答。
- 从打开串口开始逐行落盘 TX/RX、阶段和错误；连接失败或会话退出时保存两次只读 CAN/反馈快照。没有自动复位或自动恢复运动。

## 实机复测

关闭其他串口工具后，按原方式运行项目 Python/启动脚本，无需为本次修改烧录固件。控制台或界面日志中的 `[SerialLog]` 指向本次记录，目录为 `llm-pid-tuner-main/logs/can_sessions/`。最终结果日志也保存路径与失败详情。

若仍失败，保留该 JSONL，在复位前保存板端 CAN STATUS 和 MOTOR FEEDBACK。记录可区分首次在哪个阶段丢失反馈；本次软件测试不能证明物理总线故障已经消除。
