# CAN1 无轮速反馈控制：方案、复核与实现

## 目标与核查结论

本次以 Git `e9c567e` 的已跟踪源码为基线。目标是由电机内部闭环完成轮速控制，STM32 只下发目标速度；取消 PLOT 和后台轮速查询，消除上电顺序、开发板复位后因反馈未更新而无法启动或恢复的问题。车体 X/Y/YAW 的 PID 仍依据 OPS 位姿工作，这与电机内部的速度闭环是不同层级。

核查发现原来的反馈依赖有五处：

1. `zdtEmm.c` 的非零速度接口要求对应轮的反馈在 300 ms 内。
2. `mecanum_chassis.c` 要求掩码内轮速新鲜，停车依赖新的零速反馈。
3. `robot_app.c` 的运动保护、POSE 准入和恢复条件依赖轮速。
4. `llm_tuner.c` 的 ARMING 同时要求轮速新鲜和零速确认。
5. CAN 空闲恢复要求 TXOK 和 RX 均有增量，因此只取消后台查询会造成恢复条件永远不成立。

原传输层另有多邮箱跟踪、三类待发队列、故障观察窗口、卡死观察窗口和反复撤销流程。反馈慢会触发停车重发，而停车和查询又争用发送资源。以上可以从源码证明；不能仅凭这些推断真实总线所有错误都由软件引起。

## 具体优化方案与实现

### 1. 收发职责

CAN1 始终只有一个软件跟踪的在途帧。主循环完成调度；TX 中断只记录结果，RX 中断最多取三帧并解析按需诊断。每帧数据缓冲区清零到 8 字节，因为本项目 STM32 HAL 即使 DLC 较短也读取八字节。

四轮各有一个最新速度槽和一个使能槽；重复速度覆盖旧速度。按需查询只有八项 FIFO，满了返回拥塞，不把诊断队列满升级为运动故障。

发送顺序：停车轮换 → 使能 → 最新速度 → 按需诊断。存在未完成停车时，先完成停车。正常四轮目标约需四个主循环发送机会；不承诺四轮严格同时执行。

### 2. 停车和复位

STOP 清除旧速度和待发查询；若速度正在邮箱中，申请异步撤销。必须等硬件邮箱释放才发送新帧，不能把 Abort 返回 HAL_OK 当作已经撤销完成。

失败的停车帧保留，按轮轮换并至少间隔 100 ms 重试。重复 STOP 不清除已经取得的发送完成证据，也不反复撤销自身的停车帧。

空闲主循环每 1000 ms 重发一次停车，并在已有停车发送证据时刷新显式请求过的使能。这样开发板先上电、电机稍后通电时，仍会有停车和使能指令到达。显式 `MOTOR DIS` 不会被空闲刷新重新使能。

`MOTOR STOP STATUS` 的新状态 `SENT` 表示停车帧有 TXOK，输出附带 `EVIDENCE=CAN_TX_ONLY`。它不表示实际速度已测得为零。反馈记录保持真实：没有回包时 VALID 不会被伪造。

### 3. 故障与恢复

速度待发或在途期限为 50 ms。超时或提交失败锁存故障，清除软件中的非零目标；速度指令不会故障后补发。停车和使能保留限频重试。

当前 Bus-Off 会锁存故障并申请撤销在途帧，避免硬件 ABOM 恢复时重发旧速度。Bus-Off 恢复交给硬件，软件不反复 Stop/Start。Warning/Passive 和历史 PARAM/仲裁错误不单独永久阻断发送；发送结果与当前硬件状态仍受检查。

异步撤销卡住达到 500 ms 或 HAL 控制器不可用时，主循环分步执行 Stop（或在非 LISTENING 状态使用 Init）、检查/撤销旧邮箱、Start 和恢复通知。确认三个邮箱都空后才能开始新通信。失败保留故障并限频重试；没有重置 CAN1 外设或共享过滤器，也没有更改 CAN2。

恢复仅要求：上层无活动运动、控制器可用、请求掩码的停车帧均取得新的发送证据、没有在途帧。解除锁存不等待 RX、轮速 AGE 或额外 500 ms 观察窗口。随后只能响应新的运动指令。

### 4. 应用接口

保留 `MODE WORK` 和 `MODE TUNE`，移除 PLOT 枚举、入口和后台速度轮询。`MODE PLOT`、`PLOT ON`、`TELEM WHEEL/BOTH` 返回 retired 提示；`PLOT OFF` 仍可关闭遥测并回到 WORK。`TELEM POSE` 保留 OPS 位姿遥测。

`MOTOR GET <id>` 仍能一次读取轮速与状态，`MOTOR FEEDBACK` 展示缓存年龄，二者不影响正常运动准入。TUNE 的 PID 是车体位姿调参，继续依赖 OPS，但不再依赖电机编码器反馈。

保留有限数值检查、四轮等比例速度限幅、OPS 超时、RPI 主机超时、动作时限和主循环看门狗。

## 自审结果与实际边界

已针对方案再次复核并修正以下问题：

- 异步 Abort：保留在途所有权直到邮箱释放，避免新指令覆盖未撤销帧。
- Stop/Start：仅 Start 成功不能证明旧邮箱已清，恢复步骤先检查全部邮箱。
- HAL 状态：Stop/Start 失败后可能处于 READY/ERROR，重试不能一直调用只接受 LISTENING 的 Stop。
- Bus-Off：先撤销在途帧，防止 ABOM 恢复后发送故障前的目标。
- 轮速为零：运动学解算中的零速轮仍是普通速度目标，不能调用全局清队列，否则会删除其他轮刚提交的速度；显式停车单独走 FE 命令。
- 新旧使能：后到的失能覆盖旧使能，失败重试不恢复旧使能请求。
- 停车证据：故障重新使历史停车证据失效；恢复不得使用故障之前的 TXOK。

无轮速反馈的代价是不能发现单台驱动器拒绝命令、堵转或断电，也不能确认实际轮速。CAN ACK/TXOK 可能由总线上的其他节点提供，不能证明目标 ID 的电机执行正确。这是本次取消电机反馈后的真实能力边界。

MCU 复位期间没有软件运行，驱动器可能继续上一速度直到新的停车命令到达；本改动覆盖软件重新启动后的停车重发，不保证复位瞬间已经停车。说明书核查未据此确认驱动器通信失联自动停车功能，代码也没有假设它存在。

## 验证与实机验收

已完成五套 portable C 测试，其中控制层保留六组 PID、反馈监视工具、UART、OPS、运行周期测试，原 CAN 状态机测试由两组新传输测试替换。测试覆盖：

- 没有初始轮速反馈也能提交速度，最新速度合并；X/Emm 帧格式。
- 单在途发送、停车优先、异步撤销尚未完成时不发送下一帧。
- 发送超时后无 RX 恢复，旧非零目标不重发，新指令才能再次运动。
- 电机迟到对应的停车失败、轮换重试、最终停车发送完成。
- 使能后 5 ms 等待、显式失能不被空闲服务覆盖。
- 查询队列拥塞、无效 ID/校验/分包回复、时钟回绕。
- 四轮目标包含零速轮时不丢其他轮；速度等比例限幅和 NaN 拒绝。
- 撤销卡死、Start 失败后重新 Init、Bus-Off 撤销旧速度、Passive 下继续传输。

实机验收按以下顺序进行，每次记录 `CAN STATUS` 与 `MOTOR STOP STATUS`：

1. 开发板先上电，电机延后至少 5 s 上电；观察发送计数恢复增长，停车状态到 SENT，旧故障自动解除。
2. 电机先上电，再给开发板上电；随后在电机保持供电时重复复位开发板至少十次。
3. 连接串口后发送 `HOST LINK COM`、`MODE TUNE`；先用 `MOTOR MASK 0x01`、`MOTOR RUN 1 20 500` 做单轮短时测试，再恢复 `MOTOR MASK 0x0F`。
4. 确认没有后台 35/3A 查询。`MOTOR FEEDBACK` 的 AGE 持续增长应属正常，不能再据此判定通信故障；需要回包时显式发送 `MOTOR GET 1`。
5. CAN 断开后确认运动请求停止，重接后停车发送恢复且旧运动不自动继续。新运动必须重新发命令。
6. 四轮低速验证 MOVE/TURN，并查看 OPS；接线、终端电阻、供电或收发器问题仍须由真实总线测量判断。
